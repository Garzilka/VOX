# VOX

## 🚀 Основные архитектурные особенности

### 1. 🖥️ Сервер (`/Server`)
*   **Асинхронный, высокопроизводительный сервер чата на C++20, построенный на базе корутин `Boost.Asio` и событийно-ориентированной архитектуры.**
*   **C++20 Coroutines (Boost.Asio):** Все сетевые операции (чтение заголовков, отправка пакетов, жизненный цикл сокетов) реализованы на базе плоских асинхронных циклов `asio::awaitable`, что исключает проблему «адского колбэка» (Callback Hell) и обеспечивает высокую производительность под нагрузкой.
*   **Message-Driven & Dispatcher Architecture:** Сетевой уровень полностью изолирован от бизнес-логики. Обработка входящих пакетов от клиентов распределяется через `ClientMessageDispatcher`, а ответы от базы данных изолированы через лямбда-продолжения (`onResult`) внутри `BD_Dispatcher`.
*   **Ленивый потокобезопасный кэш (Lazy Cache & Request Coalescing):** Профили пользователей и кэш отношений (`Relations`) поднимаются из БД лениво — только по фактическому требованию. Защита от эффекта лавины (Cache Stampede) реализована через разделение состояний `m_ready` / `m_wakeup` и накопление ожидающих клиентов в `Pending-очередях`.
*   **Короткоживущие Stateful-сервисы (Саги):** Сложные асинхронные цепочки событий (например, сбор данных о друзьях и общих серверах при входе пользователя для рассылки статуса присутствия) инкапсулированы в изолированные одноразовые классы-роботы (`UserLoginBroadcaster`), которые уничтожаются сразу после выполнения задачи, исключая загрязнение глобальной памяти.
*   **End-to-End Безопасность (ECDH P-256 + AES-256-GCM):** Автоматический криптографический хэндшейк при каждом подключении. Обмен публичными ключами в DER-формате, генерация общего секрета через ECDH и шифрование трафика алгоритмом AES-256-GCM со строгой проверкой целостности пакетов (GCM-тег) и защитой от перехвата (12-байтовый случайный nonce).
*   **Сетевой протокол: Размерные пакеты (Big-Endian):** Строгий бинарный протокол: `[4 байта длины пакета (Big-Endian)] + [Тело (Зашифрованный JSON)]`.

### 2. 📱 Клиент (`/Client`)
Кроссплатформенное приложение на базе фреймворка **Qt**, оптимизированное для работы с асинхронным сетевым потоком.
*   **Событийный сетевой транспорт:** Реализован на базе `QTcpSocket` с реактивной обработкой сигналов `readyRead`.
*   **Потоковый парсинг пакетов:** Буферизация сетевого потока и безопасное извлечение пакетов по размеру заголовка с защитой от дробления данных в TCP.
*   **Интеграция с UI:** Динамическое управление состояниями интерфейса через менеджеры (`QUIManager`, `QChatManager`, `FriendManager`) для мгновенного обновления QML-компонентов чата.

### 3. 🚀 Лаунчер (`/Launcher`)
Стартовый узел системы, отвечающий за безопасность и актуальность клиентского приложения перед запуском.
*   Проверка версий сборки и синхронизация с сервером обновлений.
*   Первичная безопасная авторизация.

## 🛠️ Технологический стек

*   **Языки:** C++20 / C++17 (MSVC / GCC / Clang)
*   **Сетевой движок:** Boost.Asio (Async Coroutines Stack)
*   **Фреймворки и библиотеки:** Boost.Asio, Qt 6.x, OpenSSL v3.x, nlohmann/json
*   **Криптография:** OpenSSL v3.x (libcrypto)
*   **Синхронизация:** Многопоточный `AsioThreadPool`, потокобезопасные контейнеры на `std::mutex`

## 🎙️ Интеграция Медиа-сервера и Голосового Движка (LiveKit SDK + Qt Audio)

### Ключевые особенности звукового движка (`/Client`):

*   **Асинхронный захват и WebRTC-пакетизация (`QMicCapture`):** Микрофон Windows/Linux инициализируется через `QAudioSource` (стандартный формат `48000 Hz, Mono, Int16`). Данные считываются реактивно по сигналу `readyRead`, буферизируются по **960 байт (480 сэмплов)** и непрерывно передаются в WebRTC-инжектор `livekit::AudioSource::captureFrame`.
*   **Изолированный потоковый рендеринг (`PlaybackWorker`):** Для каждого удаленного участника, опубликовавшего аудиопоток, динамически генерируется собственный низкоуровневый рабочий поток (`std::thread`). Он выполняет **блокирующее асинхронное чтение** чанков звука из сети через `livekit::AudioStream::read`.
*   **Безопасный межпоточный маршалинг Qt:** Извлеченные сырые PCM-кадры маршалируются из фонового WebRTC-потока в поток вывода Qt с помощью мета-системы `QMetaObject::invokeMethod` и `Qt::QueuedConnection`. Это исключает состояние гонки (Race Condition) при обращении к аудиоустройствам.
*   **Ленивый рендеринг и буфер от заиканий сети:** `QAudioSink` для каждого участника инициализируется лениво — строго под фактическую частоту дискретизации пришедшего звука. Для предотвращения микро-фризов сети (Jitter) аппаратно выставляется кольцевой внутренний аудио-буфер на **40 мс**.
*   **Двухуровневый Hardware/Software Мут микрофона:** При активации режима "Mute" движок `QVoiceEngine` одновременно отправляет WebRTC-сигнал на медиа-сервер для изменения статуса трека у других участников и **физически очищает и перекрывает** поток байт на уровне `QMicCapture`, защищая приватность пользователя.
*   **Безопасное управление сессией переподключения:** Реализован строгий сброс медиа-ресурсов при смене комнат: при вызове `connectToVoiceServer` старая сессия `livekit::Room` полностью деинициализируется, уничтожаются все активные `PlaybackWorker`, очищается память и перезапускается стек WebRTC.


## 🔒 Безопасность сетевого потока (Пример Протокола)

При успешном подключении клиента сервер мгновенно выполняет:
1. `generateKeyPair()` — генерация пары ключей ECDH на кривой P-256.
2. Экспорт публичного ключа в ASN.1/DER и кодирование в `Base64`.
3. Отправка клиенту типа сообщения `ETypeOfMessage::Crypto`.
4. Получение публичного ключа от клиента, вычисление `m_sharedSecret` и вывод 32-байтового AES-ключа через `SHA-256`.
5. Все последующие сообщения автоматически шифруются. Пакет упаковывается в формат:
   `[4 байта net-order длины] + [12 байт IV/Nonce] + [Шифротекст JSON] + [16 байт GCM Tag]`.
